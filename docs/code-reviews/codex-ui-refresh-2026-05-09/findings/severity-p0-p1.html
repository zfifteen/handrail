HR-CR-20260509-001: iPhone follow-up composer permits duplicate submissions while one is pending

iOSOpen
ios/Handrail/Handrail/Views/ChatDetailView.swift:31 ios/Handrail/Handrail/Views/ChatDetailView.swift:355 ios/Handrail/Handrail/Views/ChatDetailView.swift:370 ios/Handrail/Handrail/Views/ChatDetailView.swift:466
Logical failureThe phone follow-up path sets pendingContinuePrompt, but the shared composer disables only when pendingSendInput is non-nil. A completed chat can therefore send the same follow-up repeatedly before the transcript echoes the prompt.
Observable consequenceCodex Desktop can receive duplicate follow-up turns, causing repeated work, confusing transcript state, and extra approval or stop events tied to the same user intent.
Minimal remediationDisable the shared composer on the relevant pending state, or pass an explicit isPending value into composer so follow-up uses pendingContinuePrompt and direct-input uses pendingSendInput.
VerificationAdd a Swift unit or view-model test that sends a follow-up, asserts the send control disables while pendingContinuePrompt is set, and re-enables after the transcript contains the prompt or an error arrives.

HR-CR-20260509-002: Approval identity is not consistently scoped by chat on iOS

iOSOpen
ios/Handrail/Handrail/Models/HandrailModels.swift:165 ios/Handrail/Handrail/Stores/HandrailStore.swift:300 ios/Handrail/Handrail/Stores/HandrailStore.swift:311 ios/Handrail/Handrail/Views/IPad/IPadApprovalReviewWorkspaceView.swift:162
Logical failureApprovalRequest.id is approvalId alone and notification approval/deny cleanup clears latestApproval by matching approvalId without also matching chatId.
Observable consequenceIf Codex Desktop reuses request identifiers across chats, an action on one chat can clear or render the pending approval for another chat. This violates the branch goal of chat-scoped approval routing.
Minimal remediationUse a composite approval identity everywhere on iOS, for example "chatId approvalId", and require both chatId and approvalId when clearing latestApproval or resolving selected approvals.
VerificationAdd iOS tests with two ApprovalRequest values sharing approvalId and different chatId, then assert notification approval/deny and selection logic affect only the matching chat.

HR-CR-20260509-003: Local notifications are suppressed when the app is backgrounded

iOSOpen
ios/Handrail/Handrail/Utilities/NotificationCoordinator.swift:215 ios/Handrail/Handrail/Utilities/NotificationCoordinator.swift:217 ios/Handrail/Handrail/Stores/HandrailStore.swift:391 ios/Handrail/Handrail/Stores/HandrailStore.swift:425
Logical failureschedule returns unless UIApplication.shared.applicationState is .active. That condition prevents local notification requests from being added while the app is inactive or backgrounded.
Observable consequenceThe user is least likely to receive local approval, input-required, failed, or completed notifications when they most need them: while Handrail is not foregrounded.
Minimal remediationInvert the decision model: suppress in-app banners only for the currently viewed chat, but allow UNUserNotificationCenter scheduling when the app is backgrounded. Keep remote-push policy separate from local notification scheduling.
VerificationAdd a notification coordinator test seam or integration harness that simulates background state and verifies a notification request is still enqueued for an unseen chat.

HR-CR-20260509-004: New approval panels can inherit stale Approved or Denied state from a previous approval

iOSOpen
ios/Handrail/Handrail/Views/ChatDetailView.swift:12 ios/Handrail/Handrail/Views/ChatDetailView.swift:253 ios/Handrail/Handrail/Views/ChatDetailView.swift:264 ios/Handrail/Handrail/Views/ChatDetailView.swift:319
Logical failureapprovalResultText is a view-wide string, not keyed to the current approval. Once set to Approved or Denied, the next approval rendered by the same ChatDetailView can display that old result before the user acts.
Observable consequenceA fresh approval can appear already approved or denied, which is a high-risk supervisory error for a local remote-control app.
Minimal remediationStore the result with the composite approval identity and display it only when the visible approval matches. Clear the local result when latestApproval changes to a different chatId/approvalId.
VerificationAdd a test or preview-state check that renders approval A, approves it, then renders approval B in the same chat view and asserts no prior result label is visible.
